# numeric/C-L-scriptnum-width

SCR-079 (`> limit ⇒ scriptnum_error ⇒ SCRIPT_ERR_SCRIPTNUM`,
`script.h:246-271`), a bounded constructor cell with **both tools green**.

## Why this cell exists

The ledger row SCR-079 was a gap: the width guard was only *incidentally*
inside other cells (`e2-numeric/within-boundary` fixed operands to one byte
and discharged the guard statically; `numeric/C-L-within-4byte` covered the
reject edge as a side condition of OP_WITHIN), so no cell *stated* the row's
claim or observed the error ordinal.  This cell states it directly: the
CScriptNum constructor is the entry point, and the observable on overflow is
the number 4 (`EQUIV_ERR_SCRIPTNUM`, Core's `SCRIPT_ERR_SCRIPTNUM`), not
merely "an error".

## Entry points

```c
uint64_t cell_scriptnum(uint64_t word, uint32_t len);  // ctor in isolation
uint64_t cell_1add     (uint64_t word, uint32_t len);  // OP_1ADD, wire 0x8b
```

`len` is the 4-bit harness length folded by `num_len8` (9..15 → 8), so the
element length ranges over every representable value 0..8; `word` is the
full 64-bit content word (2^64 byte patterns).  Both legs apply the identical
projection.

`cell_scriptnum` decodes, then push_backs `bn.getvch()` and applies the
VerifyScript tail, so on acceptance the observable carries the canonical
encoding of the decoded value.  `cell_1add` pushes the operand, runs the
opcode handler, and applies the same tail.

## L leg

`src/l_leaf.cpp` includes `build/twin_ops.h`, generated by
`findings/wave16/07-numeric-ops/tools/mk_num_leaf.py --ops OP_1ADD`.  The
constructor is the twin's own `decode_num` (`twin/runtime.inc:167-193`, the
body the generator re-binds to an 8-byte element); the push is
`st_push_num` (`twin/runtime.inc:160-164`); the opcode is `op_OP_1ADD`
copied verbatim from `twin/ops_ir.py` (`Defs.lean:1003-1007`).  The twin
maps failure to `TWIN_SCRIPTNUM`, and the generated mechanical `core_ord`
maps it to Core ordinal **4**.  Only init/push/tail/pack is cell harness.
The Lean counterpart is `Bitcoin.Interpreter.decodeNum`
(`Defs.lean:626-633`), whose `none` arm is `.error .scriptNum`.

## Symbolic claim

- Alive2 (`alive-tv --smt-to=120000`), C vs L, for both entry points:
  `2 correct transformations`, `0 incorrect`, `0 failed-to-prove`,
  `0 Alive2 errors`.
- SAW, C and L against the independent Cryptol model (`num.cry` exposed as
  `CellSpec`), 4 obligations:
  - `cell_scriptnum`:
    `~decodeOk w L ⇒ errObs 4`; otherwise the tail observable of `decode w L`
    (`obs 1 0 1 v` for nonzero, `obs 0 2 1 v` for zero).
  - `cell_1add`: `pUnary 0x8b w (clamp8 l)`, the wave-16 unary postcondition.

Exact domain: `word : 2^64` × `len ∈ {0,…,8}` ⇒ 9·2^64 inputs per entry
point.  Lengths 0..4 are the accept region; lengths 5..8 all produce error
ordinal 4.  The guard is the single comparison `len > 4`, monotone in length,
so lengths 9..520 take the same reject branch; the any-length statement is
the Lean theorem `scriptNum_width_rule` / `scriptNum_four_byte_rule_any`
(`Numeric/Interface.lean:128-158`) and `decodeNum_overflow_error`
(`Numeric/RowFaces.lean:36-45`).  The cell is the executable C↔twin half of
that composition.

## Notes and limits

- **Ordinal, not just failure.**  The reject observable is exactly `0x10`
  (`4 << 2`), so a wrong error kind (e.g. `UNKNOWN_ERROR`, 1) fails SAW even
  if both legs agree.  A same-direction mutation of the ordinal in both C and
  L is caught by SAW, not by Alive2.
- **Boundary, not just reject.**  Lengths 0..4 must *not* produce error 4
  and their decoded value is observed, so an off-by-one (`>= 4` instead of
  `> 4`) is caught by both tools.
- The three two-model deviations come from `num_core.h` and are identical in
  every numeric cell: bounded `(value,len)` element instead of `std::vector`,
  the `scriptnum_error` throw modelled as an error return carrying
  `EQUIV_ERR_SCRIPTNUM` (the value EvalScript's catch sets), and unrolled
  loops with constant indices.  The observable omits stack contents after an
  error, per the ABI (`contract/ABI.md`).
- The element width 8 is a bounded-leaf representation constant, not
  `MAX_SCRIPT_ELEMENT_SIZE`.  Lengths 9..15 cannot occur in the leaf and are
  folded to 8; the guard's monotonicity plus the Lean any-length theorem
  cover 9..520.  No operand longer than 520 bytes reaches this code
  (`interpreter.cpp:471-489` push-size gate), and for lengths 5..8 all bytes
  are irrelevant because the length check precedes every read.
- This cell does not cover: stack underflow (SCR-078), the `nMaxNumSize=5`
  CLTV/CSV sites (SCR-081), the minimality guard (SCR-083/084; off because
  flags = 0), or the completeness claim over every numeric opcode (SCR-080).
  `cell_1add` is one concrete opcode consumer, not the whole family.
- No Core patch is used (`patches: none`).
