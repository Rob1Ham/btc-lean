## Source and elisions

The C leg keeps `CheckLockTime` and the opcode case body **verbatim** from the
pin. Three text-level deviations are called out in `spec.md` and repeated here:

1. `interpreter.cpp:537-539` (`stack.size() < 1` → `INVALID_STACK_OPERATION`)
   is elided: the cell domain is exactly one operand, so the guard is
   statically false. It is SCR-051's row, not a locktime row.
2. `interpreter.cpp:557-558` (`CScriptNum nLockTime(stacktop(-1),
   fRequireMinimal, 5)`) is elided: the operand arrives already decoded, so
   the cell does not claim the 5-byte width/minimality rows (SCR-051/052).
3. `break` (continue execution on success) is spelled `return true`; the
   observable is the ScriptError the opcode leaves behind, which is what both
   legs return.

The slice fixes one input (`nIn = 0`) and one-element `vin`; SCR-132's
per-input claim is proved separately in `locktime/C-L-locktime-input-index`.

## L-leg provenance

`src/l_leaf.cpp` is a line-by-line transliteration of
`Defs.lean:272-283` (`checkLockTimeDef`) and `Defs.lean:857-865`
(`dispatchOp` wire `0xb1`). The reviewed mapping is in `src/lean_excerpt.md`.

It is **not** the generated twin. `twin/ops_ir.py:44-58` emits

```python
if (!ctx.flags.cltv) return TWIN_OK;
return TWIN_INVALID_UNSUPPORTED;
```

because the twin's handler signature `(State&, const Ctx&, const Decoded&)`
carries no transaction context. So the twin cannot express CLTV at all; the
Lean model of record can. This is filed as **F-LOCKTIME-001** in
`findings/wave16/12-locktime/report.md` (a twin-capability gap, not a
consensus divergence, and not something this task may fix — `twin/` is
outside the write scope).

## What the proofs say

- Alive2: `alive-tv build/c_cell_cltv.ll build/l_cell_cltv.ll` —
  "Transformation seems to be correct!", 1 correct / 0 incorrect.
- SAW: `llvm_verify` of both `cell_cltv` definitions against `src/cell.cry`,
  one shared printed specification, quantifier-free over
  `(i64 operand, i1 flag, i32 txLockTime, i32 txSequence)`.

Because both legs are total functions over the whole tuple space, the
equality is symmetric; `direction` lists both `L ⊑ C` and `C ⊑ L`.

## Domain notes

- `n` is the already-decoded operand, so the proved domain is all of `int64`.
  A 5-byte `CScriptNum` can only produce `-(2^39-1) .. 2^39-1`, so the result
  is strictly stronger than the row requires. No branch of the rule is
  skipped for out-of-range values: both legs treat them identically (they
  only test `n < 0`, `n < T`, `n > txlt`).
- `txTo->version` is unread by `CheckLockTime`; the harness pins it to 1.
  `CTransaction::version` is `uint32_t` at the pin
  (`primitives/transaction.h:299`), which matters for `CheckSequence`
  (SCR-128) and is why the CSV cell takes a `uint32_t` version.
- The Lean model's `ScriptNum` is `Int`; the transliteration uses `int64_t`.
  The `Int`/`int64_t` difference (F-UB-TWIN-001) is dormant here: no branch
  depends on values outside `int64_t`, and the Lean `toNat` uses are guarded
  by `n < 0` first (CLTV) or by the op-level negative rejection (CSV).

## Why the rows are full, not partial

SCR-122/123/124/125 are, between them, exactly the four decision points of
the CLTV path. The cell quantifies over every field those decisions read
(operand, flag, `nLockTime`, `vin[0].nSequence`) and both tools prove all
branches, so each row is exercised on its whole domain and both sides of its
boundary. Operand width/minimality (SCR-051/052) and per-input indexing
(SCR-132) are different rows.
