### B5 in exact terms (the blocker removed here)

Verified objects and call sites in `interpreter-O0.ll`:

```
@_ZGVZ…EvalScript…E6bnZero = internal global i64 0, align 8     ; guard
@_ZGVZ…EvalScript…E5bnOne  = internal global i64 0, align 8
@_ZGVZ…EvalScript…E7vchTrue= internal global i64 0, align 8
@_ZZ…EvalScript…E6bnZero   = internal global %__extent_storage zeroinitializer
@_ZZ…EvalScript…E5bnOne    = internal global %__extent_storage zeroinitializer
@_ZZ…EvalScript…E7vchTrue  = internal global %class.std::vector.12 zeroinitializer
```

`EvalScript` entry executes, unconditionally, for each of the three:
`load atomic i8 acquire` → `__cxa_guard_acquire` → initializer → 
`__cxa_guard_release`; and for `vchTrue`, `__cxa_atexit`. The old probe
rewrote the guard initializers to `constant i64 1`, i.e. skipped all three
initializers. `bnOne` is then zero, which is exactly what `OP_1ADD/OP_1SUB`
read.

## 2. What SAW 1.6 can actually ingest

| construct | SAW 1.6 | Alive2 v20.0 |
|---|---|---|
| `invoke` / `landingpad` | accepted; unwind edge **never taken** (model = call + no unwind) | **rejected**: `Unsupported instruction: invoke` |
| `load atomic i8` | accepted once the global has a `llvm_points_to` pre-state | rejected (see R-lane B-07b) |
| `ptrtoint` | accepted; same-allocation rule enforced by the memory model | accepted |
| `sret`, `load volatile` | n/a in C carriers | rejected (R lane only) |

Alive2 cannot ingest the engine in either carrier before or after this model.
It ingests the three model leaves (`_Znwm`, `__cxa_guard_acquire`,
`__cxa_guard_release`) as self-comparisons: 1 correct, 0 errors — a
translation check, not a proof. Logs: `logs/alive2-*.log`.

## 4. Relation to the R lane (wave16b/07)

The R-lane sanitizer findings (`B-07a sret`, `B-07b atomics`, `B-07c solver`,
`B-07d load volatile`, `B-07e callee drift`) are about `rbitcoin`. Two are
relevant to this wave:

* The **C** engine has exactly **4** atomic instructions on the whole
  `VerifyScript` path, all of them the `__cxa_guard` acquire-loads. SAW ingests
  them; the R side's 64-function `load volatile` block (B-07d) has no C
  analogue and is not something a C-side sanitizer could fix.
* Alive2's `invoke` rejection (B4 here) is the same tool wall as the R lane's
  atomic/`sret` rejections: Alive2 v20 has no exception or atomic semantics, so
  engine-level Alive2 proofs are impossible for both lanes at this tool
  version. This wave does not route around that wall; it uses SAW.
