# spec/db — consensus census and evidence records

This directory holds the rule-level traceability database for the Lean
model. Every consensus rule carries a stable rule ID, and the Lean
declarations that implement a rule carry `@[rule "<ID>"]` attributes
(kernel-side parametric attribute, `spec/core/Bitcoin/RuleAttr.lean`).

## Inventory

### Authoritative records

- `rules.yaml` — **the 726-row consensus census** and the authoritative
  source for row counts and dispositions: **676 `proven` and 50
  `obsolete`; no `implemented`, `stubbed`, or `planned` rows.** Each row
  records its ID, summary, Core anchor, Lean target, vector selectors,
  status, and source provenance. The file is generated by the census
  extraction script plus its curation/overrides layer; `make gates` checks
  that it parses, that the counts match the contract, that every anchor is
  pinned, and that Lean rule attributes cross-check. Do not hand-edit it.
- `rules-wallet.yaml`, `rules-wallet.lock`,
  `rules-wallet.obligations.tsv` — a separate **140-row wallet-level
  specification and obligation layer**, with its own lock and obligation
  register. It is never merged into the consensus census and does not
  contribute to the 726/676/50 counts.
- `axiom-manifest.txt` — generated `#print axioms` output for the 223
  named public theorems in the axiom probe. It records axiom footprints,
  not row statuses. The static gate validates the committed file's shape;
  the full probe is a local/release check.
- `axiom-manifest-wallet.txt` — the corresponding axiom manifest for the
  wallet layer.
- `axiom-audit-rows.txt` — a raw row-target axiom audit. It covers 676
  proven rows and 633 distinct `lean_target` values: 619 targets have a
  clean footprint, 10 targets fail to build, and 4 targets are missing;
  662 rows resolve to a clean declaration and 14 remain unresolved. The
  file preserves those honest gaps. It is evidence about axiom footprints
  and build availability, not a second census, and it does not change any
  row's status.
- `interface-hashes.txt` — SHA-256 hashes of the 15 frozen
  `Interface.lean` signature files.
- `vector_ids.yaml` — the row-to-corpus selector index. A rule may have no
  vectors yet; an empty selector is not a proof claim.
- `capstone.md` — the offline replay record for 13 historical mainnet
  anchor blocks, including scope and limitations.

### Raw run record — not authoritative

- `results.json` — raw output of one compiled conformance-runner
  invocation. It contains per-case pass/out-of-slice results and layer
  totals. It contains **no rule census statuses** and is not used to
  derive `status` in `rules.yaml`. It is a fixed snapshot of a finite
  corpus, not a theorem and not a coverage percentage; it is not
  regenerated by `make gates`.

## Schema (one row per rule; IDs are immutable and never renumbered)

| field | meaning |
|---|---|
| `id` | rule ID `NS-nnn` (`INV`, `TXV`, `SCR`, `SWT`, `TPR`, `BLK`, plus `SER`, `SGN`, `LED`, `POW`, `ACT`, `GEN` where a namespace applies) |
| `summary` | one-line statement of the rule |
| `check` | Core-side rule label |
| `core_ref` | `file:function:lines@commit` in the pinned Bitcoin Core tree |
| `bip_cve` | BIP / CVE / attribution string |
| `lean_target` | fully-qualified Lean declaration intended as the row's proof face; `null` until assigned. A proven row must also have its ID on at least one `@[rule "id"]` attribute; the gate checks the tag, not that the cited declaration is the one carrying it |
| `test_vector_ids` | corpus selectors (`corpus.json:case`); may be empty |
| `status` | current values are `proven` and `obsolete`. The census deliberately has no `implemented`, `stubbed`, or `planned` rows |
| `difficulty` | estimate 1–5 (`null` if unlisted) |
| `consensus` | `false` for catalogued policy/DoS boundary rows — these are documented, not modelled as consensus rules |
| `source` | extraction provenance for the row |
| `notes`, `lean_note`, `notes_extra`, `implemented_by` | internal curation annotations. They are deliberately omitted from the public census; `source` and `lean_target` retain the technical provenance. `implemented_by` was never a status |

## Ground-truth pin

Bitcoin Core **v32.99 @ `cce32b168`** is the census pin. Every row's
`core_ref` ends in the canonical suffix `@cce32b168`; the anchor-pin check
rejects any other commit tag. On a rebase, re-verify line anchors — the pin
is a checked constant, not a convention.

## Cross-check policy (`make gates`)

1. every `@[rule "..."]` attribute in `spec/core/**/*.lean` and
   `spec/proofs/**/*.lean` must name an existing row;
2. every `proven` row must have a non-null `lean_target` and its ID on at
   least one `@[rule "..."]` attribute;
3. `obsolete` rows are exempt from (2);
4. IDs must be unique.

## Status and limitations

- The census is **726 rows: 676 `proven`, 50 `obsolete`, 0 `implemented`,
  0 `planned`.** The 50 obsolete rows remain in the denominator; they are
  not silently dropped.
- `proven` means that the row's cited Lean target builds and the row ID is
  tagged. It does **not** by itself mean that the target's conclusion
  paraphrases the whole row summary. **18 of the 676 proven rows are
  explicit model residuals**: the claim is true of Bitcoin Core, but the
  current Lean model does not yet entail it. They are listed, with the
  missing link for each, in `docs/RESIDUALS.md`; they are not counted as
  fully proved against Core. Six further former residual rows
  (INV-046, SCR-008, INV-114, INV-115, INV-119, INV-138) are out-of-ledger
  (node/API or policy) obligations after the issue 22 triage; nothing was
  proved by moving them.
- The public tree contains **zero `sorry` occurrences** in `spec/core` and
  `spec/proofs` (checked by the sorry lint), and no core `native_decide`,
  `unsafe`, `partial`, or FFI hazards. A zero-sorry tree is necessary but not
  sufficient: the 18 residuals above are statement-fidelity gaps, not
  unfilled `sorry`s.
- The row-target axiom audit leaves **14 proven rows unresolved** (10
  targets in modules that do not build at audit time, 4 targets with no
  declaration). A clean axiom footprint for the other rows is not a claim
  that every target is currently buildable.
- Conformance is finite and run-specific. Runtime checks are not kernel
  theorems, and none of these records establishes byte-for-byte
  equivalence with bitcoind.
